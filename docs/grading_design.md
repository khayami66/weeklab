## 1. 背景と方針

### 1.1 なぜ Weeklab に統合するのか

設計初期（`requirements.md`）では「成績管理は別システムとして切り分け、将来API連携」としていた。
今回、**この方針を転換して Weeklab に統合する**。理由は分析にある。

「テスト結果がなぜそうなったのか」を問うには、**いつ・何時間かけて・どの順で教えたか**が要る。
Weeklab はすでに週案・進度・時数をすべて持っている。成績を別システムに切ると、この突合が
API 越しの後付けになり、実質的に使われなくなる。統合する最大の理由はここにある。

```
週案・進度（既存）          成績（今回追加）
  いつ教えたか      ×      どこで落としたか
  何時間かけたか            観点の偏り
        └──────┬──────┘
               ▼
        「なぜそうなったか」
```

### 1.2 個人情報の扱い（最重要）

**児童の氏名は一切扱わない。学年・クラス・出席番号のみで扱う。**

これにより Weeklab の既存前提（「生徒の個人情報は扱わない」ゆえに公開URL運用可）を
壊さずに済む。画面にもエクスポートJSONにも氏名は現れない。
出席番号と氏名の対応は、教員の手元の名簿にのみ存在する。

| | 扱う | 扱わない |
|---|---|---|
| 識別子 | 学年・クラス・出席番号（`3-1` の `12`） | 氏名・ふりがな・生年月日・児童ID |
| 成績 | 観点別の得点、A/B/C 判定 | 所見文、行動の記録 |

> 要件定義書 §2.4 の「生徒の個人情報は一切扱わない」は
> 「**児童の氏名は扱わず、学年・クラス・出席番号で扱う**」に更新する（v1.6）。

## 2. 確定した仕様

壁打ち（2026-09-01）で確定した内容。

| 項目 | 決定 | 補足 |
|---|---|---|
| 置き場所 | Weeklab に統合 | 週案と成績を1つのアプリで完結 |
| 識別子 | 学年・クラス・出席番号 | 氏名なし |
| 入力粒度 | **観点ごとの合計点（1人2セル）** | 設問別入力はしない |
| 対象テスト | 業者の単元テスト | 観点別配点が印刷済み |
| 観点 | 知識・技能／思考・判断・表現 の**2観点** | 第3観点は型のみ確保、MVPでは未使用 |
| 学期評定 | **観点ごとに得点率を通算**（合計点÷合計満点）してから閾値判定 | 単元ごとABCの多数決は採らない |
| 閾値 | **A: 90%以上／B: 60%以上／C: 60%未満** | 2観点共通。設定画面で観点ごとに変更可 |
| 分析 | **観点の偏り** | クラス単位・児童単位の両方 |

### 2.1 「第3観点を扱わない」判断の理由

現行学習指導要領の観点は3つだが、3つ目「主体的に学習に取り組む態度」は
ペーパーテストでは測れないというのが国の整理であり、業者の単元テストも
通常は前2観点の配点しか持たない。

したがって**本システムはテストで測れる2観点に限定する**。
通知表の3つ目の欄は、当面これまで通り教員の手元で判断する。
型（`ViewPoint`）には `attitude` を含めておき、後から入力欄を足せる形にする。

### 2.2 「得点率を通算する」判断の理由

学期に単元テストは複数回ある。それを学期の評定1つにまとめるルールが要る。

| 方式 | 判定 | 理由 |
|---|---|---|
| **合計点 ÷ 合計満点で通算**（採用） | ◯ | 満点の違う単元が混ざっても破綻しない。時数の大きい単元が自然に重くなる |
| 単元ごとにABCを出して多数決 | × | `A B B C C` のような分布で判定が不安定。境界の1点で結果が飛ぶ |
| 単元ごとの得点率を単純平均 | △ | 満点20点の小テストと100点のテストが同じ重みになる |

### 2.3 閾値 90/60 について

一般には 80/50 が広く使われるが、A/B/C の割合は法令で決まっておらず各校・各教員の裁量。
本システムは **90/60 を初期値**とし、設定画面で観点ごとに変更できる形にする。

90/60 は 80/50 より厳しいため、特に思考・判断・表現で A の割合が低く出る可能性がある。
これは1回目の集計で**分布が見えてから**判断すべき事柄であり、
閾値を定数ではなく設定値にしておく理由そのものである（計測先行）。

## 3. 型定義

`types/index.ts` に追記する。

### 3.1 観点

```ts
/**
 * 評価の観点。
 * - knowledge: 知識・技能
 * - thinking : 思考・判断・表現
 * - attitude : 主体的に学習に取り組む態度（型のみ確保。MVPでは未使用）
 */
export type ViewPoint = "knowledge" | "thinking" | "attitude";

export type GradeLevel = "A" | "B" | "C";
```

### 3.2 テストマスタ

```ts
/**
 * 業者の単元テストの定義。
 * 単元（AnnualPlan.unit_name）に紐づく。
 * max_* が 0 の観点は「そのテストでは出題されない」ことを表す。
 */
export interface TestMaster {
  test_id: string;        // "keirinkan.science.grade3.kaze-gomu"（パック内で一意）
  pack_id: string;        // "keirinkan.science.grade3"
  unit_name: string;      // AnnualPlan.unit_name と一致させる
  test_name: string;      // "風とゴムの力のはたらき"
  max_knowledge: number;  // 知識・技能の満点（0 = 出題なし）
  max_thinking: number;   // 思考・判断・表現の満点（0 = 出題なし）
  note: string;
}
```

**配置の判断：`TestMaster` はパック層ではなくユーザーデータに置く。**

業者テストの採択は学校ごとのローカル事情であり、教科書会社とテスト会社は別のことがある。
全国共有資産であるカリキュラムパックに混ぜるのは不適切。
`pack_id` / `unit_name` でパックを参照するが、実体は localStorage に持ち、
設定画面から登録・編集する。手元のテスト冊子を見ながら単元ごとに満点2つを入れるだけで、
3年・4年あわせて20件程度・年1回の作業に収まる。

> 将来、定番テストをパック同梱のプリセットとして配布することは同じ型のまま可能。

### 3.3 名簿：**持たない**（35行固定）

**在籍人数を管理する型（`ClassRoster`）は作らない。**
全クラス一律で出席番号 1〜35 の行を用意し、実際に何人いるかは記録しない。

```ts
/** 小学校の学級編制標準が35人のため、全クラス一律35行とする */
export const ROSTER_ROWS = 35;
```

#### なぜこれで足りるのか

**空いている行＝そのテストを未受験＝`null`** であり、
未受験を分子・分母から除外する仕組み（§4.1）がすでに全部を処理する。
**空行のために新しいロジックが1行も要らない。**

| 事象 | 従来案（`ClassRoster`）の作業 | 35行固定の作業 |
|---|---|---|
| 転入 | 設定画面で人数を +1 | **なし**（空いている番号に打ち始めるだけ） |
| 転出 | 設定画面で欠番に追加 | **なし**（打つのをやめるだけ） |
| 初期設定 | 7クラス分の人数を入力 | **なし** |
| 在籍28人のクラス | 28行 | 35行（29〜35行は常に空欄） |

得られるもの：`ClassRoster` 型・`syncClassRoster` 同期処理・設定画面1セクション・
永続化キー1つ・DataSource メソッド2つが**すべて不要になる**。G2 が明確に軽くなる。

#### 運用ルール（1つだけ守る必要がある）

> **転出した児童の出席番号を、転入児童に再利用しない。**

再利用すると、同じ番号の下に別人の得点が混ざり、通算得点率が誰のものでもなくなる。
35行あるので、転入児童は**使われていない末尾の番号**（例：在籍28人なら29番）に入れる。
これは実務でも事故りやすい箇所なので、入力画面に注意書きを出す。

#### 定数にする理由（設定値にしない）

小学校の学級編制標準は35人であり、制度上これを超えない。
設定値にすると初期設定の項目が増えるだけで、得るものがない。
将来 40人学級（中学校等）に広げるときは `ROSTER_ROWS` を変えて再デプロイすればよく、
カリキュラムパックの更新と同じ運用に収まる。

### 3.4 得点（生データ）

```ts
/** 1人・1テスト分の得点。未受験は null（0点ではない）。 */
export interface TestScore {
  student_no: number;
  knowledge: number | null;  // null = 未受験（通算の分母から除外）
  thinking: number | null;
}

/** 1クラス・1テスト分の実施記録。 */
export interface TestResult {
  test_id: string;
  class_code: string;
  conducted_on: string;   // "YYYY-MM-DD" 実施日。学期の集計範囲判定に使う
  scores: TestScore[];    // クラス全員分
}
```

**未受験を `null` にするのは必須。** 欠席を 0 点として扱うと通算得点率が壊れ、
評定が実態と乖離する。`null` は分子・分母の両方から除外する。

### 3.5 閾値設定

```ts
export interface GradeThreshold {
  viewpoint: ViewPoint;
  a_min: number;  // A の下限（%）初期値 90
  b_min: number;  // B の下限（%）初期値 60。これ未満が C
}
```

**`TeacherSetting` には入れず、独立キー `weeklab.{year}.grade_thresholds_v1` に置く。**
理由：`TeacherSetting` へのフィールド追加は既存 localStorage データの後方互換対応
（読み込み時の補完）を伴う。実際 `teacher_type` 追加時に修正コミット `ed0f761` が必要になった。
同じ轍を踏まないよう、新規データは新規キーに分離する。

### 3.6 判定結果（派生）

```ts
export interface ViewPointResult {
  viewpoint: ViewPoint;
  earned: number;      // 通算獲得点
  max: number;         // 通算満点（未受験分を除く）
  rate: number;        // earned / max（0-1）
  grade: GradeLevel;
  test_count: number;  // 通算に含めたテスト数
}

export interface StudentGrade {
  class_code: string;
  student_no: number;
  by_viewpoint: ViewPointResult[];
}
```

`max === 0`（全テスト未受験、またはその観点の出題なし）の場合は判定不能とし、
A/B/C を返さず画面上は `—` で表示する。

### 3.7 観点の偏り（分析）

```ts
/**
 * 既存の ProgressHealth と同じ形にそろえる（level + message）。
 * gap が負 = 思考・判断・表現が弱い
 */
export interface ViewpointBalance {
  scope: "class" | "student";
  class_code: string;
  student_no: number | null;  // scope === "class" なら null
  knowledge_rate: number;     // 得点率（0-1）
  thinking_rate: number;
  gap: number;                // thinking_rate - knowledge_rate
  level: HealthLevel;         // ok / warn / alert（既存型を再利用）
  message: string;            // "思考・判断・表現が 18pt 低い" 等
}
```

判定初期案：`|gap| < 10pt` = ok ／ `10〜20pt` = warn ／ `20pt 以上` = alert。
進度ヘルスチェック（±3／±5時間）と同じ考え方。**この数値は実データを見て調整する前提**。

## 4. ロジック（`lib/grading.ts`）

既存の `lib/` と同じく**純粋関数のみ**。UI から完全に分離し、Vitest で検証する。

```ts
/** 閾値を当てて A/B/C を返す */
function judgeGrade(rate: number, threshold: GradeThreshold): GradeLevel;

/** 期間内の TestResult から1人分の観点別通算と判定を出す */
function computeStudentGrade(
  class_code: string,
  student_no: number,
  results: TestResult[],
  masters: TestMaster[],
  thresholds: GradeThreshold[]
): StudentGrade;

/**
 * クラス全員分（出席番号 1..ROSTER_ROWS を走査）。
 * 全テスト未受験の番号（＝空行・在籍していない番号）は判定不能として返し、
 * 分布・平均・偏り分析からは除外する。
 */
function computeClassGrades(
  class_code: string,
  results: TestResult[],
  masters: TestMaster[],
  thresholds: GradeThreshold[]
): StudentGrade[];

/** 観点の偏り（クラス単位・児童単位） */
function computeViewpointBalance(grades: StudentGrade[]): ViewpointBalance[];

/** 期間で TestResult を絞る（conducted_on ベース） */
function filterResultsByPeriod(results: TestResult[], from: string, to: string): TestResult[];
```

### 4.1 通算の計算式

観点 `vp` について、期間内の全テストを走査する。

```
earned = Σ (score[vp] が null でないテストの得点)
max    = Σ (score[vp] が null でないテストの満点)
rate   = earned / max          // max === 0 なら判定不能
grade  = rate*100 >= a_min ? "A" : rate*100 >= b_min ? "B" : "C"
```

### 4.2 テストで必ず押さえるケース

- 未受験（`null`）が分子・分母の両方から除かれること
- **一部のテストだけ受験した児童が、受験した分だけで正しく判定されること**（転入児童のケース）
- 全テスト未受験（`max === 0`）で判定不能になり、A/B/C を返さないこと
- **在籍していない番号（空行）が分布・平均・偏り分析の分母に入らないこと**
- 満点の異なるテストが混在しても通算が正しいこと
- `max_knowledge === 0` のテスト（片観点のみ）が混ざっても壊れないこと
- 境界値：ちょうど 90% は A、ちょうど 60% は B、59.9% は C
- 閾値を変更すると判定が追随すること（90/60 決め打ちになっていないこと）

## 5. 画面設計

### 5.1 `/grades` 成績処理（新規）

3つのタブで構成する。

**タブ1：得点入力**

**クラスを主軸にし、テストを列として横に並べる**（テスト主軸にしない。理由は §5.4）。

```
クラス [3-1] [3-2] [3-3] [4-1] [4-2] [4-3] [4-4]

表示する列： [✓]風とゴム [✓]こん虫 [✓]太陽 [✓]光 [✓]電気     [全部表示] [最新のみ]

        風とゴム        こん虫         太陽          光           電気
番号   知技  思判表   知技  思判表   知技  思判表   知技  思判表   知技  思判表
  1  [ 45][ 40]   [ 48][ 42]   [ 40][ 35]   [ 44][ 38]   [   ][   ]
  2  [ 30][ 25]   [ 35][ 30]   [ 28][ 22]   [ 31][ 27]   [   ][   ]
─────────────────────────────────────────────  ← 5行ごとに罫線
  6  [ 50][ 46]   ...
 28  [ 38][ 41]   ...
 29  （在籍なし・薄く表示）
 35
                                                        [ 保存 ]
※ 転出した児童の番号は再利用せず、転入児童は空いている末尾の番号に入れてください
```

- **出席番号は常に 1〜35 行**（`ROSTER_ROWS`）。在籍人数は設定しない
- 空欄＝未受験（`null`）。0 と明確に区別する
- 一度も得点が入っていない番号は薄く表示し、どこまでが実在児童か分かるようにする
- 番号の再利用を防ぐ注意書きを常時表示
- **入力効率の設計は §5.4 にまとめた。G3 の必須要件とする**

**タブ2：学期評定**
```
集計期間 [2026-04-06] 〜 [2026-09-30]

3-1        知識・技能        思考・判断・表現   受験
番号   得点率  評定      得点率  評定       テスト数
 1      92%    A          78%    B            5
 2      64%    B          58%    C            5
 7      88%    B          71%    B            2 ⚠ 転入
...
分布   A:8 B:19 C:3      A:2 B:21 C:7    （在籍28名）
```
- 通算得点率と A/B/C。校務支援システムへの入力元になる
- **クラス末尾に A/B/C の分布**を出す（閾値調整の根拠になる）
- **受験テスト数を並べる。** 転入等で受験数が少ない児童は、少ないテストで評定が決まって
  しまうため、教員が気づけるようにする（他より明らかに少ない場合は印を付ける）
- 得点が1件も無い番号（在籍なし）は行ごと表示しない。分布の分母にも入れない

**タブ3：観点の偏り**
```
クラス別      知識・技能  思考・判断・表現   差
3-1              81%          63%        -18pt  ⚠
3-2              79%          71%         -8pt
...
⚠ 3-1 は思考・判断・表現が 18pt 低い

要注目の児童（差が 20pt 以上）
3-1  12番   知技 90%  思判表 55%   -35pt
```

### 5.2 `/settings` への追加セクション

- **評定の閾値**：観点ごとの A/B の下限（初期値 90/60）。**固定値ではなくここで変更する**
- **テストマスタ**：単元ごとのテスト名・観点別満点の登録

在籍人数の設定は**置かない**（§3.3 の35行固定により不要）。

閾値エディタのイメージ：
```
評定の閾値
              A の下限    B の下限
知識・技能      [ 90 ]%    [ 60 ]%
思考・判断・表現 [ 90 ]%    [ 60 ]%      [ 既定値に戻す ]

※ B の下限未満が C。学期評定タブで A/B/C の分布を見てから調整できます
```

### 5.3 集計期間の指定について

学期の区切り（2学期制／3学期制）は学校差があるため、
**MVP では設定に持たず、集計画面で日付範囲を直接指定する**。
`TeacherSetting` にフィールドを増やさずに済み、どの学期制でも動く。
プリセット（前期／後期）は運用しながら必要になった時点で足す。

### 5.4 入力効率の設計（最優先事項）

移行時の入力量は **7クラス × 5テスト × 約30人 × 2観点 ≒ 2,100セル**。
1セルあたり2秒なら約70分、4秒なら約140分。**UI の作り込みが1時間以上の差を生む。**

ボトルネックは打鍵速度ではなく、**紙と画面を往復する視線移動と、行を見失うこと**。
以下はすべてそこを潰すための設計であり、G3 の必須要件とする。

#### ① クラス主軸にして画面遷移をなくす（効果最大）

紙の名簿は「1クラス1枚に全テストが並ぶ」形が普通。
画面もそれに合わせれば、**紙1枚＝画面1枚**になり、テストを切り替えるたびの遷移がゼロになる。

| 方式 | 移行時（5本まとめて） | 通常運用（採点直後に1本） |
|---|---|---|
| テスト主軸（テストを選んでから入力） | クラス×テストで**35回**画面を切り替える | 1回 |
| **クラス主軸＋テストを列に**（採用） | クラスごとに**7回**だけ | 列を「最新のみ」に絞れば同じ |

画面は1つ。**列の表示/非表示で両方の使い方に対応する**（コンポーネントを2つ作らない）。

#### ② 入力方向を紙に合わせて切り替えられるようにする

手書き名簿は観点ごとに縦に並んでいることが多い。
1人ずつ横に2つ打たせると、**紙の上で視線がジグザグに動いて遅くなる**。

```
[縦]（既定）：1列を35人分打ち切ってから次の列へ  ← 紙が縦並びならこちら
[横]        ：1人の2観点を打ってから次の行へ
```

Enter を押したときの移動先がこの設定で変わる。**既定は縦**。
実際の名簿を見て合わないようなら切り替えられるので、事前に決め打ちしない。

#### ③ キーボードだけで完結させる（マウスを触らせない）

- `Enter` / `↓` `↑` `←` `→` `Tab` をすべて効かせる
- 未受験は**何も打たずに `Enter`** で次へ（空欄のまま飛ばす）
- テンキーだけで手が動くこと。**保存以外でマウスに手を移す場面を作らない**
- 数字2桁で自動的に次へ送る「オートアドバンス」は**採用しない**
  （満点が5点・100点のテストで誤爆する。`Enter` 明示のほうが速くて安全）

#### ④ 行を見失わせない

- **入力中の行を行全体でハイライト**する
- **5行ごとに罫線を濃くする**（紙の名簿と同じ視覚リズム）
- 出席番号を左端に大きく固定表示（横スクロールしても消えない）
- 現在の行番号を画面のどこかに大きく出す

行がずれたまま数十人分を打つのが最悪の事故。**気づくのが遅いほど手戻りが大きい。**

#### ⑤ 入力直後に検算する（後から間違いを探さない）

- 満点超過はその場で赤くする
- 保存時に**クラス平均・入力件数**を表示し、明らかな外れ値に気づけるようにする
- 「28人入力／未受験2名」のように件数を必ず出す（打ち漏らしの検出）

#### ⑥ 小分けにする

1クラス1テスト＝約60セル＝**1〜2分**。この単位で保存できるようにする。
「2,100セル」ではなく「1〜2分の作業を35回」と見えるほうが、実際に着手できる。

#### 採用しないもの

| 手段 | 不採用の理由 |
|---|---|
| 手書き名簿のOCR / カメラ読み取り | 手書き数字の認識精度が低く、**検算に入力以上の時間がかかる**。一度きりの移行に見合わない |
| 音声入力 | 数字の誤認識が多く、訂正操作でかえって遅くなる |
| Excel からの一括貼り付け | 元データが紙なので今回は効果ゼロ。将来 Excel 資産が出てきたら検討（実装は軽い） |

#### 恒久的な解決は「紙をやめること」

今回の2,100セルは**一度きりの移行コスト**。
次のテストから**採点直後にそのまま Weeklab に入力**すれば、
紙に書いてから写す二度手間が消え、入力量は「1テスト60セル」に平準化される。
移行を終えたら、紙の名簿は記録の正本ではなくバックアップに位置づけを変えるのがよい。

## 10. 設計の弱点（正直な評価）

自分で書いた設計について、承知のうえで残している弱点を明示しておく。

### 10.1 「なぜ」の答えは半分しか出ない

統合の理由は「テスト結果がなぜそうなったのかを分析したい」だった（§1.1）。
だが現在のスコープ（観点の偏りのみ）で分かるのは
**「思考・判断・表現が弱い」という事実まで**で、その原因には届かない。

本来の狙いである**週案データとの突合**（配当時数に対して何時間かけたか × その単元の結果）は
§9-5 で「次段階」に送っている。データはすべて揃っているので追加ロジックだけで足せるが、
**そこまで作らないと統合した意味が半分になる**ことは認識しておく。

→ G4 完了後、最優先で着手すべきはこれ。

### 10.2 入力量が実際に回るかは未検証 → **解消（2026-09-04 実測）**

> **実測結果**：1クラス1テストの入力に **1分35秒**（画面に慣れていない1回目）。
> 移行全体は 35回 × 1分35秒 ≒ **約55分**。下の「たぶん大丈夫と判断しない」という
> 但し書きに従って測った結果、**見立て（3〜6時間）を大きく下回った**。
> 機械側（打鍵→描画のレイテンシ）も実測済みで、実施機では p50 32ms・最適化不要。
> 詳細は `開発ログ.md`「G3 入力速度の実測」。**この節の懸念は解消済み。**


移行量は約 **2,100セル**（7クラス × 5テスト × 約30人 × 2観点）。
§5.4 の設計で視線移動と画面遷移は潰したが、**それで足りるかは実測しないと分からない**。

G3 ができたら、**まず1クラス1テスト（約60セル）を実際に入力して所要時間を測る**。
そこから残り34回分を見積もり、必要なら §5.4 の設計をさらに詰める。
設計段階で「たぶん大丈夫」と判断しない。

なお 2,100セルは**一度きりの移行コスト**であり、
運用に乗れば「1テスト60セル」に平準化される（§5.4 末尾）。
