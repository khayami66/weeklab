### セッション5: 運用面・配信形態の確定

**壁打ちした論点**
1. 管理職への事前確認 → **済み**
2. 年度切り替え運用
3. データのバックアップ・端末間移行
4. 教科書改訂への対応
5. 生徒個人情報の扱い

**Webアプリ vs ローカルの比較**
- 配布性・多端末利用・LINE連携・保守性すべてでWebアプリが有利
- Next.js はそもそもWebアプリ前提
- 生徒個人情報を扱わないのでセキュリティリスクは低い

**決定事項**
| 項目 | 決定 |
|---|---|
| 配信形態 | **Webアプリ**（Vercel、無料枠、限定URL） |
| 利用端末 | 自宅PCのみ（学校PCはセキュリティ制約で導入困難） |
| 年度管理 | 年度ごとにデータ分離、年度切替機能をMVPに入れる |
| アーカイブ | 凍結保存（`WeeklyPlan` スナップショット方式） |
| アーカイブ保持期間 | MVPは無期限（多ユーザー化したら見直し） |
| バックアップ | JSONエクスポート/インポートをMVPに追加 |
| 教科書改訂 | 最新パックのみ保持（旧パックは破棄） |
| 過去年度の単元名一貫性 | アーカイブは WeeklyPlan で保存されるため影響なし |
| 生徒個人情報 | 扱わない |
| 成績管理 | 別システムで切り分け、将来API連携で疎結合 |

**データ設計の追加**
- `TeacherSetting.school_year` を追加
- localStorage キーに年度プレフィックス：`weeklab.{year}.*`
- `ArchivedWeek` / `ArchiveMetadata` / `FullSnapshot` 型を追加
- `/archive` 画面を追加
- `/settings` に年度切替モーダル・エクスポート/インポートパネル

### セッション7: 設計レビューと壁打ち

**対応**
- Phase 1 着手前に設計ドキュメントを網羅的に確認
- 潜在的論点を12項目抽出し、順次合意形成

**合意された方針変更**

1. **進度管理：前週確定型に変更**
   - 従来案：`ClassProgress` から全コマ自動計算
   - 新案：**各クラスの週先頭コマをユーザーが確定** → 以降は `LessonMaster` 順で自動表示
   - 理由：実授業は進度がずれるため、週はじめに再確定する方が現実的
   - データ層は変えず、UI層の運用のみ変更
   - キー：`weeklab.{year}.first_lesson.{monday_date}`

2. **進度ヘルスチェック機能を追加**
   - 期待累計 = 年間配当時数 × (現在週 / 全週数)
   - 差 ±3時間で warn（amber）、±5時間で alert（rose）
   - ホーム・週案・進度画面にバッジ表示
   - 新ファイル：`lib/healthCheck.ts`

3. **週案と月次集計を分離**
   - 週案表示・印刷：**週実施・実施累計**のみ（月実施を除外）
   - 月次集計は別画面 `/monthly` に切り出し
   - 印刷対応 `/print/monthly`（教育委員会報告用）
   - 松戸市様式とも整合（元様式も月実施を含まない）

4. **iPad 対応**
   - MVP では試験不要
   - Phase 18 で時間があれば iPad Chrome を触る程度
   - 本格対応はユーザー拡大時

5. **LessonMaster 運用**
   - 「2単元先行整備」：現単元＋次単元を常にカバー
   - 未整備時は `lesson_title = "(未作成)"` でフォールバック、時数カウントは継続

**確定した個別項目**

- プロジェクト名：**weeklab**（Next.js プロジェクト名も統一）
- 始業式日：**2026-04-06**
- クラスコード形式：**`3-1`**（ハイフン区切り、3年×3クラス＋4年×4クラス＝7クラス）
- 月〜土：**最初から6行設定**（土曜授業がない日が多いが、入力がなければ空扱い）

- 週あたり授業数：**18コマ**（3年2コマ×3クラス ＋ 4年3コマ×4クラス）

### 成績処理層の設計（2026-09-01 壁打ち・設計確定）

**背景**
- 成績処理の時期（9月）に入り、ユーザーから「週案作成に加え、成績処理もこのシステム一つで
  完了できるようにしたい」との要望。Phase 13（週案印刷）より優先することにした。

**方針転換：成績処理を Weeklab に統合する**
- 設計初期（`requirements.md`）では「成績管理は別システムとして切り分け、将来API連携」だった
- **転換の理由は分析にある。**「テスト結果がなぜそうなったのか」を問うには
  「いつ・何時間かけて・どの順で教えたか」が要る。Weeklab はすでにそれを持っている。
  別システムに切ると突合が API 越しの後付けになり、実質的に使われなくなる

**個人情報の扱い（ユーザー判断）**
- **児童の氏名は扱わず、学年・クラス・出席番号のみで扱う**
- これにより「生徒の個人情報を扱わないゆえに限定URL運用可」という既存前提を壊さずに済んだ
- 要件定義書 §2.4 / §6.4 を「氏名は扱わない」表現に更新（v1.6）

**壁打ちで確定した仕様**

| 項目 | 決定 | 却下した案と理由 |
|---|---|---|
| 入力粒度 | 観点ごとの合計点（1人2セル） | 設問別○×は分析解像度が高いが入力量が跳ねる |
| 観点 | 知識・技能／思考・判断・表現 の2つ | 第3観点はペーパーテストで測れない。型のみ確保 |
| 学期評定 | 観点ごとに得点率を通算（合計÷合計満点） | 単元ごとABCの多数決は境界で不安定 |
| 閾値 | **A=90% / B=60%**（2観点共通・設定変更可） | 一般的な 80/50 より厳しめ。分布を見て調整する前提 |
| 分析 | 観点の偏り | 週案データとの時数突合は次段階 |
| テスト | 業者の単元テスト | 観点別配点が印刷済みで、マスタ登録が軽い |

**設計上の判断（`grading_design.md` に詳述）**
- **`TestMaster` はパック層でなくユーザーデータに置く** — 業者テストの採択は学校ごとの
  ローカル事情。全国共有資産であるカリキュラムパックに混ぜるのは不適切
- **`GradeThreshold` は `TeacherSetting` に入れず独立キーにする** — `teacher_type` 追加時に
  既存 localStorage データの補完が必要になり修正コミット `ed0f761` を要した。同じ轍を踏まない
- **未受験は `null`（0点ではない）** — 0点扱いにすると通算得点率が壊れ評定が実態と乖離する
- **名簿は35行固定にして型を持たない**（ユーザー提案・採用）
  - 当初案は `ClassRoster`（クラスごとの在籍人数＋欠番）を新設する形だった
    （`grade_configs` は「3年3クラス」という組数しか持たず人数がないため）
  - ユーザーから「1クラス35名がマックス。児童数に関係なくシートを35行にすれば
    転出入の削除・追加の手間が減る」との提案。**採用した**
  - **成立する理由：空行＝全テスト未受験＝`null` であり、未受験を分子分母から除外する
    仕組みがすでに全部を処理する。空行のための新ロジックが1行も要らない**
  - 削れたもの：`ClassRoster` 型・同期処理・設定画面1セクション・永続化キー1つ・
    DataSource メソッド2つ。G2 が軽くなった
  - **運用ルール1つだけ必要**：転出児童の番号を転入児童に再利用しない
    （同じ番号に別人の得点が混ざり通算が壊れる）。入力画面に注意書きを出す
- **集計期間は設定に持たず画面で日付範囲指定** — 2学期制/3学期制の違いに依存しない

### G3 入力速度の実測 ― 機械側（2026-09-04）

`grading_design.md` §10.2 が求めた実測のうち、**機械側（打鍵レイテンシ）**を先に計測した。
「35行 × 最大10列 = 350個の制御された入力が、1打鍵ごとに全セル再レンダーされる」ことの
体感影響を数字にするのが目的。

**方法**
- 本番ビルド（`next build` → `next start -p 3210`）に対して計測。dev サーバーは
  React dev ビルドのぶん遅く、悲観的な数字になるため使わない
- ヘッドレス Edge（CDP）で打鍵を自動発行。**間隔は人の速度に合わせて 150〜250ms/打鍵**
- 1打鍵あたり2つ取る：`task`（JSの仕事量）と `paint`（画面に出るまで）
- `Emulation.setCPUThrottlingRate` で CPU 1〜6倍遅い機械を近似
- React を外した素の `<input>` を同じ経路で測り、計測ハーネスの下限（4.4ms）を把握
- スクリプトは scratchpad（`measure-input.mjs` ほか）。localStorage は
  専用ポート・専用 user-data-dir で汚染なし

**結果（10列＝5テスト分・人の打鍵速度・打鍵→描画 p50 / p95）**

| CPU | p50 | p95 | 体感 |
|---|---|---|---|
| **等速（この開発PC）** | **32 ms** | 44 ms | 気づかない |
| 2倍遅い | 86 ms | 108 ms | わずかに遅れる |
| 3倍遅い | 136 ms | 179 ms | 遅れが分かる |
| 4倍遅い | 193 ms | 255 ms | はっきり遅い |
| 6倍遅い | 374 ms | 856 ms | 打鍵に画面が付いてこない |

**結論：この開発PCで成績処理を行うため、最適化は不要。**
105打鍵を通して最大 52ms。打ち続けても詰まらない。
ユーザー確認により、9月の移行入力（2,100セル）はこの開発PCで実施する。

**訂正：「重ければセル単位のメモ化を入れる」（G3 の記録）は打ち手として誤り**

CPU4倍で列数を振ると、入力数を5倍にしてもレイテンシは1.4倍にしかならない。

| 列数 | 入力の数 | 打鍵→描画 p50 |
|---|---|---|
| 2列（1テスト） | 70個 | 139 ms |
| 10列（5テスト） | 350個 | 193 ms |

**コストの大半はセル数によらない固定費**であり、セル単位のメモ化も、画面の
「表示するテスト」で列を減らす回避策も効き目は限定的。将来この画面が重い機械に
載ることがあれば、固定費の正体を特定してから手を打つこと。

なお `isDirty` が毎レンダーで走らせている `JSON.stringify` を主犯と疑ったが、
単体ベンチで 0.09ms/回であり**無罪**だった（コードを読んだ印象で犯人を決めない）。

**計測そのものの落とし穴（dev-knowledge に記録済み）**
- 当初 35ms/打鍵で打っていたため、CPU3→4倍で p50 が 147ms → 500ms に急落する
  「性能の崖」が2回再現した。**これは人の4〜7倍の速さで打鍵したことによる待ち行列**で、
  計測の人工物。人の速度に直すと崖は消えて線形になった
- → `pitfalls/2026-09-04-input-latency-benchmark-artifacts.md`、
  手順は `playbooks/frontend-responsive-preview.md` 3章
